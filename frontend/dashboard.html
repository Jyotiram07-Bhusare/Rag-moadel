The bar

The rubric: 14 hard checkpoints

Every check is pass or fail. No scores, no partial credit. A lesson ships only when all 14 pass.

Architecture & reasoning

How the system works, and why

One loop, one rule: nothing reaches a learner until an independent judge has said pass on every check.

Design decisions

✅

Binary checks, not 1–10 scores

Scores drift and models hedge around 7/10. A pass/fail check forces a decision and produces a precise reason that can be fed straight back to the generator.

⛔

A hard cap on retries

Max 1–2 retries means the loop always terminates and cost is bounded. If the cap is hit, the lesson is held for human review. It is never shipped by default.

⚖️

Two-layer judge

Rules measure what is measurable (sentence length, defined terms, structure): cheap and repeatable. An LLM judge covers meaning (accuracy, analogy quality), using a different model at temperature 0.

🎯

Feed back reasons and quotes

The retry prompt names the failing check and quotes the offending sentence, and says "keep the rest". This cuts regressions. The log shows when a retry fixes one thing but breaks another.

🧠

Memory makes it self-evolving

Every failure is counted across runs. When a check fails repeatedly, a rule is promoted into the generator prompt. Run 3 starts better than run 1. Human feedback is stored too.

🔌

Frontend and engine are decoupled

The UI only reads a small event stream. Swap the demo engine for LangGraph, n8n or a Python API without touching the interface.

⚠️

Trade-offs we accept

Rule checks can be shallow: a bolded word is not proof of understanding. Strict rubrics cost more retries. We reduce this with the LLM judge, human spot-checks, and tuning from the failure stats.

🪞

Honest demo mode

The demo engine has no LLM: its drafts are pre-written, some with planted flaws. But the evaluator really reads the text, so a lesson edited in the lab fails for real reasons. Learned rules make the demo's first draft cleaner, the way a real LLM would respond to them.
